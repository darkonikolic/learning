# Partial failure + degradation thinking

**Theme:** Reality rarely all-red / all-green—design **continuation with degraded modality mix** ethically.

Stereotypical scenario:

Git history accessible → contextual blame feasible  

Transactional **DB unavailable** transiently→ pivot to filesystem / structural reasoning + queue metrics only until safe reconciliation window reopened

Discuss **repair ownership**: who rewinds speculative edits produced under uncertain evidence—assistant must annotate confidence decay explicitly.

Practice slices:

Go **worker debugging** while DB explorer is down: rely on structured logs + queue metrics and narrow hypotheses—no guessing row-level truth.

Symfony **CQRS** work while integration tests are red: rely on SPEC + code structure; label conclusions as **degraded confidence** until tests pass again.

Mandatory lab cruelty: sabotage exactly **one** integration intentionally—observe whether assistant **DETECT → REPAIR speculative assumptions → CONTINUE** without catastrophic overreach.

Discuss **tool degradation ladders**: MCP browser offline → degrade to cached docs retrieval path if policy allows—not hallucinating release notes verbatim.

Discuss **verification**: degraded chains produce **narrower conclusions** loudly labelled—not fake full certainty camouflage.

### Checklist

- [ ] Outputs under degradation carry **confidence downgrade banner** conspicuously—not footnote-muted only.
