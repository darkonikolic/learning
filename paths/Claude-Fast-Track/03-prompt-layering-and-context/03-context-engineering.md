# Context engineering

Context engineering is the deliberate construction of the context window for a specific task. It is not "paste everything and hope." It is selecting exactly what Claude needs for this operation and excluding what creates noise.

The surgeon's kit principle: a surgeon does not carry the entire hospital supply closet into the operating room. They carry exactly the instruments needed for this procedure. Context works the same way. Irrelevant context is not neutral — it competes with relevant context for Claude's attention and burns tokens.

---

## What context engineering is not

Pasting the entire codebase and asking Claude to "figure out what's relevant." This gives Claude the maximum surface area for distraction.

Relying on conversation history. What you said ten messages ago is in the context window but carries less weight than what you say now. Do not assume Claude reconstructed your constraints from history.

Assuming Claude knows your file structure. Even with CLAUDE.md listing paths, Claude does not have the file content — only the paths. If you want Claude to know the content of a specific file, include it explicitly or point directly to it.

---

## Three-step context construction

**Step 1: What does Claude need to know?**

For this specific task, what is the domain knowledge, what are the constraints, what decisions have already been made that affect this work?

Do not ask "what might be relevant." Ask "what is necessary." If removing it would cause Claude to make a wrong decision, include it. If removing it wouldn't change the output, leave it out.

**Step 2: What files are actually relevant?**

Read those files explicitly in your prompt. Not the whole codebase — the specific files Claude needs to understand to complete this task correctly.

For implementing a handler: the handler interface, an adjacent handler for style reference, the store interface Claude will call.

For fixing a bug: the specific function that contains the bug, the test that exposes it.

For writing a SPEC: the problem statement, constraint list, one adjacent SPEC for consistency.

**Step 3: What decisions were made earlier?**

State them explicitly. Do not rely on chat history to carry them.

```
Prior decisions relevant to this task:
- Task IDs are sequential integers generated by the store, not the handler (decided in session 1).
- All timestamps use time.Time, stored in UTC, formatted as RFC3339 in JSON responses.
- Handler functions do not receive a context.Context — request context is r.Context().
```

These three lines cost a few tokens. Omitting them risks Claude making different decisions that break existing code.

## Context for different task types

| Task type | Include | Exclude |
|-----------|---------|---------|
| Feature implementation | SPEC acceptance criteria, relevant interfaces, one adjacent handler for style | Unrelated packages, test files for unrelated features |
| Bug fix | Exact error message, failing test, the specific function that fails | Whole file if the function is isolatable |
| Refactor | Files being changed, their callers, interface definitions | Implementation files of packages not being touched |
| Architecture review | High-level structure, key interfaces, existing patterns | Implementation details of individual functions |
| SPEC writing | Problem statement, constraints, one adjacent SPEC | Existing implementation (specify what SHOULD be, not what IS) |
| Code review | Changed files only | Everything not in the diff |

The "one adjacent example" rule: for style consistency, one example of the existing pattern is usually enough. Three examples of the same pattern is redundant — pick the most representative one.

## Context for task-api: practical examples

**Implementing GET /tasks:**

Include:
- docs/specs/get-tasks.md (the SPEC)
- internal/handler/task.go (already has CreateTask for style reference)
- internal/store/store.go (the interface Claude will call)

Exclude:
- internal/domain/ (not relevant to this handler)
- *_test.go files (not implementing tests this turn)
- main.go (routing wiring is a separate step)

Message opener:
```
Implement GET /tasks handler. 

Read these files before starting:
- internal/handler/task.go (existing handler for style reference)
- internal/store/store.go (interface to call)

SPEC: docs/specs/get-tasks.md — acceptance section is binding.
```

**Debugging a broken test:**

Include:
- The exact test failure output (copy-paste from terminal)
- The specific test function
- The specific handler function the test is calling

Exclude:
- Other test functions in the file
- Other handler functions
- The store implementation (unless the bug is in the store)

Message opener:
```
TestGetTasks is failing. Failure:

--- FAIL: TestGetTasks (0.00s)
    task_test.go:47: expected status 200, got 405

Test function: internal/handler/task_test.go TestGetTasks
Handler function: internal/handler/task.go GetTasks

Read both functions and identify why the test gets 405.
```

**Writing a SPEC for PATCH /tasks/:id/complete:**

Include:
- Problem statement: "Complete a task by ID. Idempotent."
- Constraints: 404 if not found, 200 if already complete (idempotent, not 409)
- docs/specs/post-tasks.md (adjacent SPEC for consistency in format and section names)

Exclude:
- The current handler implementation (you're writing what SHOULD be, not documenting what IS)
- Internal store implementation details

Message opener:
```
Write SPEC for PATCH /tasks/:id/complete. Do not look at any existing implementation.

Constraints:
- 404 if task does not exist
- 200 if task is already complete (idempotent — not 409)
- 200 on successful completion

Format: match the structure of docs/specs/post-tasks.md exactly.
Output: docs/specs/patch-tasks-complete.md
```

## Pruning stale context

After a long session, early context becomes noise. What you established in message 2 is still "present" but competing with everything said since. Two techniques:

**`/compact`:** Claude summarizes the conversation into a compressed representation. Good for switching sub-problems within the same session. The summary captures key decisions. Use before pivoting from one feature to another.

**Explicit re-statement:** State the current context explicitly at the start of a new sub-task. Don't rely on `/compact` always capturing what matters.

```
Setting context for this task: we are on step 5 (store integration). Steps 1-4 are complete and passing tests. The handler parses the body, validates, and now needs to call store.AddTask(). Prior decision: store.AddTask returns (Task, error) — not (id, error).
```

This re-statement costs 50 tokens and saves the risk of Claude acting on stale context.

**When to use each:**

| Situation | Use |
|-----------|-----|
| Pivoting to a different feature in the same project | `/compact` |
| Starting a new phase (new major feature) | New session |
| Continuing same feature, 15+ messages deep | Explicit re-statement |
| Context window warning appearing | `/compact` then explicit re-statement |

## The context budget

Context is finite. Every token you spend on irrelevant files is a token not available for Claude's reasoning about the actual task.

For complex tasks, the context budget allocation matters:

| Content | Approximate tokens | Priority |
|---------|-------------------|---------|
| CLAUDE.md (lean) | 500-1000 | Always — already loaded |
| SPEC file | 500-1500 | High for implementation tasks |
| Relevant source files | 1000-5000 | High — but only the relevant ones |
| Prior decisions (re-stated) | 200-400 | Medium — only what affects this task |
| Unrelated files | 1000-10000 | Zero — exclude entirely |

If including a file means excluding something more important, the file should stay out. Claude with the right 3000 tokens of context outperforms Claude with 10000 tokens of mixed-relevance context.

## Signs your context engineering needs work

Claude implements something you said was out of scope. Per-turn constraints were crowded out.

Claude uses a pattern inconsistent with the rest of the codebase. The style reference file was not included.

Claude's implementation doesn't match the SPEC. Either the SPEC wasn't in context, or it was included but lost in too much surrounding content.

Claude asks clarifying questions about things you thought were established. Prior decisions were not re-stated explicitly.

Fix: each of these symptoms has a clear cause. Remove irrelevant content. Add the missing reference. Re-state decisions explicitly. Keep CLAUDE.md lean.
