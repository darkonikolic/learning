# CLAUDE.md authoring — the project brain

CLAUDE.md is Claude's persistent project memory. It loads automatically at the start of every session. Its contents are always in context, which makes it powerful and expensive simultaneously. What you put there shapes every interaction. What you omit forces Claude to guess.

The fundamental discipline: CLAUDE.md carries what Claude cannot derive from reading the code, and nothing else.

---

## Location hierarchy and loading order

| File | Scope | Loaded when | Who commits |
|------|-------|------------|-------------|
| `~/.claude/CLAUDE.md` | Global — all projects | Every session, every project | You — personal |
| `./CLAUDE.md` or `./.claude/CLAUDE.md` | Project root | Every session in this project | Team — committed |
| `./subdirectory/CLAUDE.md` | Subdirectory | When Claude works in that subdirectory | Team |
| `./CLAUDE.local.md` | Personal override | Every session, gitignored | You — not committed |

All files load and merge. Subdirectory CLAUDE.md adds to project CLAUDE.md — it does not replace it.

For task-api: one `./CLAUDE.md` at the project root is sufficient. Add subdirectory CLAUDE.md only if a subdirectory has genuinely distinct rules that don't belong in the project root file.

---

## Full CLAUDE.md template

```markdown
# [Project Name]

## Project
[One sentence: what this is, what it does]

## Stack
- Language: [language and version]
- HTTP: [framework or stdlib + key facts]
- Storage: [type + key implementation detail]
- Test: [framework or stdlib]
- External dependencies: [list or "none — stdlib only"]

## Key paths
- Entry point: [path]
- Handlers: [path]
- Domain: [path if applicable]
- Config: [path if applicable]

## Constraints
- Must: [non-negotiable behavior]
- Must not: [things that must never happen]
- Must not: [second constraint]

## Conventions
- [Naming rule or pattern]
- [Error handling pattern]
- [Other non-obvious convention]

## Known gotchas
- [Non-obvious decision a new developer would get wrong]
- [Non-obvious constraint not visible from reading the code]

## Rules (load when relevant)
See .claude/rules/ for detailed rule files.
- [rule-name]: [one-line description of what it enforces]
```

Fill every section that applies. Delete sections that don't. Empty sections are clutter.

## task-api CLAUDE.md example

```markdown
# task-api

## Project
Go HTTP API for task management — POST /tasks, GET /tasks, PATCH /tasks/:id/complete.
In-memory storage. No auth. No database.

## Stack
- Language: Go 1.22
- HTTP: stdlib net/http with http.NewServeMux()
- Storage: in-memory []Task with sync.RWMutex in internal/store/store.go
- Test: stdlib testing + net/http/httptest
- External dependencies: none (stdlib only)

## Key paths
- Entry point: main.go
- Handlers: internal/handler/task.go
- Store interface + implementation: internal/store/store.go
- Domain (validation): internal/domain/task.go
- Specs: docs/specs/
- Plans: docs/plans/

## Constraints
- Must not add external packages (no gorilla/mux, no gin, no gorm, no uuid library).
- Must validate all input at handler boundary before calling store.
- Must return application/json Content-Type on all responses including 4xx and 5xx.
- Must use sync.RWMutex: RLock for reads, Lock for writes.

## Conventions
- Task IDs: UUID-format strings, generated by store.AddTask() — not by the handler.
- Error responses: {"error": "human readable message"} — single "error" key only.
- HTTP status codes: 400 invalid input, 404 not found, 409 conflict, 500 internal.
- Timestamps: time.Time, stored in UTC, serialized as RFC3339.

## Known gotchas
- Task struct is immutable after creation except for Completed bool and CompletedAt time.
- Store mutex must be held for the full read-modify-write cycle on Complete().
- created_at is set by store.AddTask(), not by the caller. Handler must not set it.

## Rules (load when relevant)
- spec-before-code: require SPEC file before implementing any feature
- stdlib-only: no external Go packages permitted
```

This CLAUDE.md tells Claude everything it needs and nothing it doesn't. Every line answers: "Would Claude make a wrong decision without knowing this?"

## What belongs — decision table

| Belongs in CLAUDE.md | Does NOT belong in CLAUDE.md |
|---------------------|------------------------------|
| Stack and versions | Full spec or requirements (link to them) |
| Non-obvious must/must-not constraints | Git history or recent changes |
| Key file paths | Task state ("currently implementing X") |
| Conventions not derivable from reading code | Code patterns Claude can see by reading files |
| Known gotchas that trip up new contributors | Decisions with full reasoning (just the constraint) |
| Pointers to rule files and spec files | Long explanations of why a decision was made |

The test for any CLAUDE.md entry: "If Claude reads the actual code in the project, would it be able to derive this?" If yes — leave it out. Claude can read code. CLAUDE.md is for what code alone doesn't tell you.

## What makes a constraint entry effective

**Weak (vague):**
```
Be careful about concurrency.
```
Claude cannot verify if it's following this.

**Strong (binary):**
```
Must use sync.RWMutex: RLock for reads (GetAll, GetByID), Lock for writes (AddTask, Complete).
```
Claude can verify: is it using RLock for GetAll? Yes or no.

**Weak:**
```
Use good error handling.
```

**Strong:**
```
Must not swallow errors. Every error returned by the store must be checked and handled — not assigned to _.
```

Rule: constraint must be checkable by a code reviewer without asking Claude to interpret it. Binary language: "must", "must not", "always", "never". Not "prefer", "try to", "when possible".

## Size discipline

| CLAUDE.md lines | Status | Action |
|-----------------|--------|--------|
| Under 80 | Lean and focused | Ideal |
| 80–150 | Acceptable | Watch for bloat |
| 150–200 | Borderline | Audit: can anything move to rules/ or docs/? |
| Over 200 | Bloated | Split required |

When over 200 lines, split using this pattern:

Move from CLAUDE.md:
```markdown
## Handler rules
- Must validate all request body fields before calling domain layer.
- Must not call store methods directly — must go through domain.
- Must return 400 with {"error": "..."} for validation failures.
- [10 more lines of handler-specific rules]
```

Create `.claude/rules/handler-contracts.md` with the detail. Replace in CLAUDE.md:
```markdown
## Rules (load when relevant)
- handler-contracts: validation and response format rules for handlers
```

One line in CLAUDE.md. The detail lives where it's needed.

## Updating CLAUDE.md over time

**During a session — discovered constraint:**
```
Add this to CLAUDE.md under "Known gotchas": The store's Complete() method 
must acquire a write lock for the full read-modify-write cycle. A read lock 
for the check followed by a write lock for the update creates a TOCTOU race.
```

Claude will edit CLAUDE.md directly. Review the diff before accepting.

**Between sessions:**
Any constraint you find yourself re-stating in multiple sessions belongs in CLAUDE.md. If you write "remember, we're using stdlib only" in session 4, that fact should have been in CLAUDE.md from session 1.

**Cleaning CLAUDE.md:**
Review it at the start of each new milestone. Remove entries that are no longer true. Remove entries Claude can now derive from reading the (grown) codebase. Remove anything that hasn't shaped a decision in the last month.

CLAUDE.md is not an archive. It is a working document.

## CLAUDE.md vs .claude/rules/ vs session context

| Content | Where it goes |
|---------|--------------|
| Project identity, stack, versions | CLAUDE.md |
| Hard must/must-not (short form) | CLAUDE.md constraints section |
| Hard must/must-not (detailed with examples) | .claude/rules/<name>.md |
| Path-specific rules | .claude/rules/<name>.md with paths frontmatter |
| This-session-only constraint | Message layer |
| Non-recurring constraint | Message layer |

The rule: if it applies to every session and every task in this project, CLAUDE.md. If it applies to every session but only to certain file paths, a rule file. If it applies only to this task or session, the message.

## Checklist

- [ ] CLAUDE.md exists at project root.
- [ ] Every constraint uses "must" or "must not" — not "try to" or "prefer".
- [ ] Stack section includes versions and key implementation details (not just language name).
- [ ] Key paths listed so Claude navigates without guessing.
- [ ] Known gotchas capture non-obvious decisions.
- [ ] No full specs or requirements — only pointers to docs/specs/ files.
- [ ] No session-state or recent-change notes.
- [ ] Each entry answers: "Would Claude make a wrong decision without this?"
- [ ] CLAUDE.md is under 200 lines.
- [ ] Rules section references .claude/rules/ files for detailed policy.
